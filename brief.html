rtl-env · results brief · October 2026

Training environments for chip-verification agents

Coding agents already read, edit, compile and test hardware designs. To get better at it, the model inside the agent needs practice on hard tasks with a score it can't argue with. We build those: "find and fix the bug" tasks from real Verilog designs, each graded by a simulator, served in the same tool loop agents already use.

What the agent bars show. Working in our environment, the model fixed 30 of 40. That is what a training environment needs: tasks an agent can make progress on, a mix of passes and failures so the reward carries signal, and a grade it can't game. The 10 it still failed, 7 of them on the UART, are the room left to improve.

What the one-shot bars show. We picked these 40 from tasks the model had already tried in a single answer, mostly failures, so that bar is low by design. On the same tasks, the tool loop flipped 21 from fail to pass and broke none of the 9 one-shot passes: the tasks reward actually investigating, compiling and testing, which is the skill agents are trained for.

On a fair sample the one-shot numbers are 31% on the two open-source designs and about 78% on the interrupt controller. Our first, simpler designs were too easy (the model solved 559 of 560), which is why we moved to these.

No gaming seen. In 40 runs the model never rewrote a whole file to dodge the work, and 38 of 40 submissions were compiled or tested after the last edit. Cost was about $0.17 per run at list prices.

How a task is made

Start from a design that works, break it, keep only breaks we can catch

step 1

A working design

A correct Verilog design with a written spec. 11 are written in-house; 2 are open-source efabless IP (Apache-2.0, credited).

step 2

Break it automatically

Our injector makes small realistic edits: a flipped comparison, a wrong constant, a swapped signal, a deleted line. It also removes logic for "fill in the missing part" tasks.

step 3

Keep only catchable bugs

Each broken version is simulated. If our checks can't tell it from the original, it is thrown away, so every task has a real, detectable problem.

step 4

Grade by simulation

The fix runs against hidden checks: hand-written tests, plus a side-by-side run against the original on thousands of random cycles, at several parameter settings.

real task · timer IP · one injected bug and the hidden check's verdict
- else if (apb_we & (PADDR[16-1:0] == PWM1CFG_REG_OFFSET)) PWM1CFG_REG <= PWDATA[16-1:0];
+ else if (apb_we & (PADDR[16+1:0] == PWM1CFG_REG_OFFSET)) PWM1CFG_REG <= PWDATA[16-1:0];

grader: fail · run 5 cycle 1329: output PRDATA = 0x4dc2, expected 0xf16c

The model sees the spec and the broken file. It never sees the original, the tests, or the random inputs the grader uses.

The agent environment

A sandbox where a model works like an engineer

Each task opens as a private workspace holding only the spec and the design. The model can read and search files, make exact edits, compile, and run a light set of practice tests. When it submits, the full hidden grade runs once and returns pass or fail. That pass or fail is the training reward.

The practice tests are deliberately weaker than the grade: fewer tests, one parameter setting, and different random inputs. Passing practice does not guarantee a pass, which is what keeps a model from simply tuning to the tests.

Spec audit

We use model failures to find mistakes in our own specs

A task is only fair if the spec fully describes the correct design. Real IP has quirks, and if the spec misses one, a model that follows the spec gets marked wrong. Training on that teaches the wrong lesson.

So we look for places where many independent model answers "fix" code that was already correct. Our tool swaps each module of a failed answer into the original design one at a time and simulates it, which pinpoints exactly where the answer's behavior differs. Then we check each spot by hand.

What we haven't shown yet

Open questions, stated plainly

  • Training transfer. We have not yet trained a model on these tasks and measured it on an outside benchmark. That is the next proof point.
  • Bug realism. Today's bugs are generated edits. Real bugs are often design misunderstandings across several lines. Next we add tasks built from real bug-fix commits in open-source hardware projects.
  • Sample size. The agent result is one model, one run per task, 40 tasks on 3 designs.
  • Hard designs. We have 3 designs at the level where frontier models struggle; we are adding more.
